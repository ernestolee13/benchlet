# 발견 단계 (절차 1~2)

아래를 그대로 따른다. `{project_path}` 는 대상 프로젝트다. 코드를 바꾸지 않는다. 읽기만 한다.

너는 `{project_path}` 프로젝트에서 **판정 미니벤치 후보를 발견**한다. 코드를 바꾸지 않는다. 읽기만 한다.

## 벤치 서명 (후보마다 반드시 붙인다)

```
goal      무엇을 재나
            compliance  규정·지침 준수 여부        classify  카테고리 분류        route  경로·도구 선택
            derive      원문에서 도출한 값·주장 검증  gate      임계값 통과 판정      fit    질문·선택지·형식 정합
            rank        순서형 우선순위·점수
answer    정답 형식.  binary(예/아니오, 위반/통과) | choice(n)(단일 정답 다지) | ordinal(k)(순서형 점수)
prob_use  확률을 쓰나. accuracy_only(맞고 틀림만) | threshold(임계로 게이트, 임계 곡선 필요) | calibrated(확신값 자체를 씀, 보정 지표 필요)
label     정답 근거.  machine(검증기·규칙 실행) | constructed(규칙대로 심음) | judged(사람 판정) | outcome(사후 결과 조인)
unit      항목 단위.  sentence | post | record | query | pair
```

다중 정답은 후보가 아니다. 갈라서 두 후보로 만든다.

goal 의 경계. 규칙 조항으로 「올릴 수 있나」를 가르면 compliance, 임계값(점수·건수)으로 통과를 가르면 gate, 카테고리 이름을 고르면 classify, 원문에서 도출한 값·주장을 검증하면 derive, 경로·도구를 고르면 route. 둘 다 같아 보이면 질문 문장의 술어를 따른다(「위반하는가」「충족하는가」는 compliance).

## 읽는 순서 (2026-09-30 1회차 뒤 개정)

**라벨이 이미 있는 곳부터 찾는다.** 승인·반려·정정 상태 컬럼(`status`, `approved`, `rejected`, `feedback`, `corrected`), verdict·audit 테이블, 사후 결과 테이블. 여기서 나온 후보는 라벨 경로 1번(생성 불필요)이고 맨 위에 둔다.

그다음 CLAUDE.md·AGENTS.md·README → 규칙·린트·점수·리뷰 스크립트 → DB 스키마·마이그레이션 → 워크플로·크론·핸들러 → 로그·최근 기록 → 테스트·픽스처. 임계값 게이트는 `min_score`, `threshold`, `>=`, `limit` 를 grep 으로 찾는다. 파일 머리만 읽고 넘기지 않는다. **판정이 일어나는 자리**를 찾는다. 코드 안의 `if score > N`, 규칙 목록, 라우팅 표, 승인·반려 상태, 분류 라벨, 사용자 정정 기록이 신호다.

## 게이트 (하나라도 걸리면 후보에서 뺀다)

- 판단·품질평가·규칙 준수·사실 도출이어야 한다. **지식 질문은 아니다**
- 모델이 답할 수 있어야 한다. 「사람들이 어느 쪽을 골랐나」 같은 **모델 너머의 문제는 아니다**
- 정답이 규칙이나 원문에서 **제3자가 도출 가능**해야 한다. 「좋은가」「자연스러운가」 같은 취향은 아니다
- 원천 규칙에 soft 등급이 있으면 그걸 binary 위반으로 묻지 않는다
- **규칙표나 라우트 표를 주고 그 적용을 묻는 것은 판단이다.** 「표를 주면 독해」라고 낮추지 않는다. 표를 빼서 지식 문제로 만들지도 않는다

## 개인정보

후보 설명·예시에 사람 이름, 이메일, 전화, 계정 ID, 회사·고용주 도메인, 내부 IP, 키·토큰을 쓰지 않는다. 필요하면 역할·업종·번호로 치환한다.

## 산출: `discovery.md`

후보 8~12개. 갤러리 조회가 불가능한 환경이면 첫머리에 한 번 「비슷한 벤치 조회 불가」라 적고 `benchlet list` 의 로컬 벤치와 대조한 결과를 후보마다 「겹침」 줄에 적는다. 각 후보에

```
질문 (한 문장. 극성을 정답 0 과 맞춘다)
서명  goal / answer / prob_use / label / unit
원천  파일 경로와 줄, 또는 테이블·컬럼

왜 중요한가  이 판정이 틀리면 실제로 무슨 일이 나나
위험  개인정보·취향·모델 너머·soft 규칙·다중 정답 중 해당하는 것
예시 항목 1개  상태·질문·선택지·정답·근거. 개인정보 치환 후
```

## 커버리지 (2026-09-30 추가)

후보는 `goal` 축을 **최소 4개 이상** 걸친다. 한 goal 에 3개 넘게 몰리면 나머지는 「추가 후보」로 내린다. 프로젝트에 그 goal 의 판정 지점이 정말 없으면 「없음」과 이유를 적는다. `answer` 축도 binary 만이 아니라 choice(n) 또는 ordinal 후보를 최소 1개 넣으려 하고, 없으면 없다고 적는다.

## 벤치 계획 (2026-09-30 개정. 개수는 고정하지 않는다)

마지막에 **첫 벤치로 추천하는 후보 1개**와 이유. 그리고 **권장 벤치 계획표**를 낸다.

- 후보마다 **라벨 경로**를 먼저 정한다. 1 있는 라벨 샘플링(승인·반려, 정정, verdict, 사후 결과가 이미 있음. 생성 불필요) / 2 규칙 심기 / 3 패턴 모방 생성(실제 입력을 씨앗으로, 분포 유지, 사람 검수 필수). **1번이 있으면 최우선으로 올리고 「생성 불필요」라고 적는다**
- 게이트를 통과한 후보를 서명(goal·answer·unit)이 다른 것끼리 묶는다. 같은 서명은 하나로 합친다
- 등급을 붙인다. 핵심(운영 게이트·승인 큐·발행 경로에 직접 붙음), 보조(규칙은 명시됐으나 운영엔 안 붙음), 나중(라벨을 먼저 만들어야 함)
- 권장 = 핵심 전부 + 라벨 경로 1·2번인 보조. 「나중」은 선결 작업과 함께 목록에만
- 벤치마다 권장 항목 수. 기본 40~60. 클래스마다 8건 이상, threshold 면 60 이상, calibrated 면 100 이상, 지금 데이터로 만들 수 있는 상한 안에서
- 벤치마다 사람이 읽을 항목 수 × 20초의 검수 시간(라벨 경로 1번은 표본 검수라 5분의 1)과 비용(항목·팔당 $0.00003)을 적고 합계를 낸다. 합계가 60분을 넘으면 「나중」부터 내리되 표에는 남긴다
- 표 형식: 벤치 / 서명 / 등급 / 라벨 경로 / 권장 n / 클래스 수 / 검수 시간 / 비용 / 선결 작업
- 게시하려면 레지스트리 형식(항목 스키마·매니페스트)을 그대로 따라야 한다는 것을 표 아래 한 줄로 알린다

사용자가 이 표에서 행을 끄거나 n 을 바꾼다. 그 뒤에만 항목을 만든다.

그리고 **후보로 올리지 않은 판정 지점**을 게이트 사유와 함께 3개 이상 적는다.
