# 실행 가이드 (사용자의 에이전트가 읽고 스스로 맞추는 요건)

실행은 게시의 조건이 아니다. 키가 없으면 올리기만 해라. 레지스트리가 기준 팔을 돌려 결과를 붙인다. 직접 돌리려면 어느 게이트웨이든(OpenRouter, Vercel AI Gateway, LiteLLM, 사내 게이트웨이, 로컬 vLLM) 아래 요건을 **네 에이전트가 확인하고 맞춘다.** 우리가 provider 마다 코드를 두지 않는다.

## 요건 (확률 팔을 쓰려면 전부 만족)

1. **로그확률이 와야 한다.** `logprobs: true`, `top_logprobs: 8` 을 보내고 응답 `choices[0].logprobs.content[0].top_logprobs` 에 라벨 토큰(A, B, …)이 실제로 있어야 한다. `supported_parameters` 같은 플래그를 믿지 말고 **한 번 불러서 확인**한다
2. **추론을 끈다.** 추론 모델은 추론 토큰이 `max_tokens` 를 먹고 첫 토큰 분포가 「생각의 첫 토큰」이 된다. 에러가 없어 조용히 틀린다. 게이트웨이마다 끄는 법이 다르다(OpenRouter `reasoning: {enabled: false}`, 벤더별 `thinking` 옵션, 모델 자체에 non-thinking 변형). 응답의 `completion_tokens_details.reasoning_tokens` 가 0 인지 본다
3. **provider 를 고정한다.** 같은 모델이라도 provider 마다 로그확률 유무·정밀도가 다르다. 라우팅이 새면 결과가 섞인다. 고정할 수 없는 게이트웨이면 응답의 provider 필드를 항목마다 기록한다
4. **`max_tokens: 1`, `temperature: 0`.** 답은 글자 하나다
5. **재현성.** 같은 항목을 3회 불러 P(A) 편차가 0.05 를 넘으면 그 조합은 쓰지 않는다. **확률값 종류 수**가 항목 수의 절반 아래면(반올림된 로그확률) 쓰지 않는다
6. **라벨 질량.** 상위 8개 토큰 중 라벨 토큰의 확률 합이 0.5 아래인 항목은 오류로 두고 세지 않는다(모델이 문장을 시작하려 한 것)
7. **극성 반전.** 이진은 A·B 뜻을 뒤집어 두 번 부르고 평균 낸다. 다지는 선택지를 항목별 결정론적 시드로 섞는다
8. **로그확률이 안 오면 생성 팔로.** 구조화 출력이나 단일 토큰 생성으로 정확도만 재고 `prob_source: none` 으로 표시한다. 보정 지표는 N/A

## 스모크 (전량 전에 5건, 1센트 미만)

뻔한 양성 3건과 음성 2건을 팔 전부에 돌린다. 요건 1·2·5·6 을 여기서 같이 확인한다. 하나라도 걸리면 그 조합을 빼거나, 뻔한 걸 틀리면 질문 결함으로 보고 질문을 고친다.

## 우리가 확인한 조합 (2026-09-30, OpenRouter)

`results/or_verified.json`. 그 밖의 게이트웨이는 확인하지 않았다. 네가 확인한 조합은 결과 파일의 `arm` 에 `base_url`(호스트만)·`provider`·`retest_spread`·`distinct_p` 를 남겨라. 게시하면 갤러리가 조합표에 모은다.

## 병렬·재시도·합치기 (2026-10-05)

- `benchlet run --concurrency 6`(기본)이 항목 단위로 동시에 부른다. 순서와 집계는 순차와 같다. 제공자 속도 제한(429)과 5xx 는 1, 2, 4, 8, 16초 대기 뒤 다시 시도한다.
- 한 팔만 실패했으면 `benchlet run --bench <b> --arms <팔> --merge` 로 그 팔만 다시 돌려 기존 결과 파일에 합친다. 항목 해시가 같을 때만 된다.
- 선택지가 10개를 넘는 벤치는 첫 토큰 라벨 질량 실패가 는다. 가능하면 선택지를 줄이거나 번호 라벨로 묻는다.
